# S32K344 중앙 도메인 담당 범위 정리

## 1. 전체 ECU Interface 구조 정의

중앙 S32K344에서 각 ECU와 어떤 정보를 주고받아야 하는지 정의한다.

예시:

- Window ECU → Domain
  - 창문 위치
  - 동작 상태
  - Anti-Pinch 상태
  - Fault 상태

- Domain → Window ECU
  - Open / Close / Stop 요청
  - 목표 위치

> CAN ID, Start Bit, DLC 등 실제 통신 세부사항은 통신 담당자가 설계한다.

---

## 2. Request / State / Event / Fault 규칙 정의

도메인에서 사용하는 데이터를 다음과 같이 구분한다.

- **Request**: 특정 기능 실행 요청
- **State**: 현재 차량 또는 ECU 상태
- **Event**: 순간적으로 발생한 사건
- **Fault**: 오류 및 비정상 상태

예시:

```c
typedef enum
{
    WINDOW_REQ_NONE,
    WINDOW_REQ_OPEN,
    WINDOW_REQ_CLOSE,
    WINDOW_REQ_STOP
} WindowRequest_t;

typedef enum
{
    WINDOW_STATE_UNKNOWN,
    WINDOW_STATE_OPENING,
    WINDOW_STATE_CLOSING,
    WINDOW_STATE_STOPPED,
    WINDOW_STATE_FAULT
} WindowState_t;
```

Request와 State는 반드시 분리해서 관리한다.

## 3. S32K344 Domain SW Architecture 설계

중앙 도메인은 통신 방식 자체보다 차량 기능의 판단과 제어에 집중한다.

권장 구조:

```text
S32K344 Domain
│
├── Vehicle State Manager
├── Request Manager
├── Domain Manager
├── Arbitration
├── Smart Access Logic
├── Window Logic
├── Climate Logic
└── Fault / Safety Logic
```

통신 계층과 도메인 계층은 분리한다.

```text
CAN / UART
    ↓
Communication Layer
    ↓
------------------------
Domain Interface
------------------------
    ↓
Domain Logic
```

도메인 코드에서는 가능하면 Raw CAN Frame이나 UART Byte를 직접 처리하지 않는다.

## 4. FreeRTOS Domain 처리 구조 설계

통신 Task와 Domain Task를 분리한다.

```text
[통신 담당]

CAN Rx Task
CAN Tx Task
ESP32 Communication Task
        ↓
Queue / Shared Interface
------------------------------
        ↓
[Domain 담당]

Domain Task
Vehicle State Manager
Arbitration
Fault / Safety Logic
```

Domain Task의 주요 역할:

1. Request 확인
2. Vehicle State 확인
3. 실행 조건 판단
4. 충돌 요청 Arbitration
5. 실행 Command 생성

## 최종적으로 중앙 S32K344 담당자가 준비할 핵심 4가지

1. **ECU 간 필요한 정보 정의**
2. **Request / State / Event / Fault 규칙 정의**
3. **S32K344 Domain SW Architecture 설계**
4. **FreeRTOS 기반 Domain 처리 구조 설계**

CAN Signal Matrix와 ESP32 ↔ S32K344 UART Protocol의 실제 통신 상세 설계는 통신 담당자가 수행하고, 중앙 도메인 담당자는 필요한 데이터와 인터페이스 요구사항을 정의하고 검토한다.

# S32K344 도메인 담당자 중점 스터디 상세계획

> 기준 보드: **S32K344-WB / S32K344**
>
> 개발 환경: **S32 Design Studio 3.6.x + S32K3 RTD**
>
> 대상 역할: **Central / Domain Controller 담당자**
>
> 방향: S32K144에서 이미 수행한 GPIO, Timer, Interrupt, ADC, PWM, UART, CAN 주변장치 기초는 최대한 압축하고,  
> 실제 프로젝트에서 도메인 제어기가 담당하는 **상태 취합 → 요청 검증 → 판단/중재 → 명령 분배 → 결과/Fault 통합**을 중심으로 학습한다.

---

# 1. 스터디 방향

기존 S32K344 스터디는 MCU 전체 기능을 폭넓게 다루는 14일 과정이었다.

하지만 현재 프로젝트에서 담당하는 S32K344는 **개별 액추에이터를 직접 구동하는 ECU가 아니라 중앙 도메인 제어기**이므로 학습 우선순위를 다음과 같이 변경한다.

```text
기존 S32K344 전체 학습
GPIO / Timer / Interrupt / PWM / ADC / DMA / UART / SPI
CAN / CAN FD / FreeRTOS / Ethernet / Safety / HSE
                    ↓
              담당 역할 기준 압축
                    ↓
RTD 구조와 S32K3 차이
        ↓
FreeRTOS / 주기 제어
        ↓
ECU Interface
        ↓
Request / State / Event / Fault
        ↓
요청 검증 및 중재
        ↓
상태 최신성 / Heartbeat / Timeout
        ↓
Smart Access / Climate / Ambient 등 중앙 판단
        ↓
통합 / Fault / HMI 결과 관리
```

---

# 2. SR 기준 도메인 제어기 핵심 역할

Central Controller가 중점적으로 수행할 부분은 다음과 같다.

### 1. 기능별 ECU 상태 취합

대상 예:

- Power Window Controller
- Function Controller
- Sensing Controller
- Vision 결과
- ESP32 / 모바일 사용자 요청
- VSS 상태 또는 Event

도메인에서는 각 장치를 직접 제어하기보다 **각 ECU가 제공하는 상태와 결과를 저장하고 관리**한다.

---

### 2. 사용자 / 센싱 요청 검증

예:

```text
ESP32
  ↓
Door Unlock Request
  ↓
Domain
  ├─ Digital Key 유효?
  ├─ 사용자 근접 상태 유효?
  ├─ COMM_FAULT 없음?
  ├─ 현재 차량 상태에서 허용?
  └─ 다른 상위 우선순위 명령과 충돌 없음?
        ↓
Function ECU에 Unlock 목표 명령
```

---

### 3. 요청 중재 및 기능 허용 판단

동시에 여러 요청이 발생했을 때 어떤 요청을 허용할지 판단한다.

예:

```text
Remote Window Close
        +
Anti-pinch 발생
        ↓
Domain에서는 Anti-pinch 상태를 우선 반영
        ↓
추가 Close 요청 제한
```

실제 모터 보호 동작은 Window ECU가 수행하더라도  
도메인은 이후 요청을 허용할지 판단할 수 있어야 한다.

---

### 4. 자동 기능 연계 판단

대표 기능:

- Smart Access
- Predictive Climate
- Auto Re-lock
- 자동 환기
- Ambient Lighting
- 차량 상태 기반 경고 / HMI 표시

---

### 5. Fault 및 상태 최신성 관리

도메인에서는 단순히 값만 저장하면 안 된다.

```text
ECU State
+
Last Update Time
+
Valid
+
Fault
+
Communication State
```

를 함께 관리해야 한다.

예:

```text
Window Position = 50 %
```

라는 값이 있더라도 2초 동안 새로운 상태가 수신되지 않았다면

```text
현재 Window Position = 50 %
```

라고 신뢰해서는 안 된다.

따라서 다음 개념이 중요하다.

- Heartbeat
- Update Period
- Timeout
- Data Freshness
- COMM_FAULT
- SENSOR_FAULT
- FUNCTION_FAULT
- Recovery 조건

# 3. 기존 S32K144 학습 내용 압축 기준

| GPIO | **S32K3 SIUL2 차이만 확인** |
| Clock | **Clock Tree 위치와 Peripheral Clock 확인만** |
| Timer | **FreeRTOS Tick/주기 Task 이해에 필요한 정도** |
| Interrupt | **NVIC + ISR → Task 전달만 복습** |
| PWM | 제외 |
| ADC | 제외 |
| SPI | 제외 |
| 일반 UART | ESP32 Interface 이해용으로만 간단히 |
| CAN 기본 | 송수신 구현 반복하지 않음 |
| CAN FD Bit Timing | 통신 담당자 영역. 개념만 이해 |
| DMA | 선택 |
| Ethernet | 선택 |
| HSE | 선택 |
| Safety | Watchdog/Fault 관점만 간단히 |
| FreeRTOS | **중점** |
| Request / State 구조 | **최중점** |
| ECU 상태 취합 | **최중점** |
| Timeout / Heartbeat | **최중점** |
| 통합 판단 로직 | **최중점** |

## 제출

# Day 2. S32K144 내용 초압축 복습

이 Day의 목적은 새로운 주변장치 기능을 배우는 것이 아니다.

**S32K144에서 했던 작업이 S32K344에서는 어디가 달라지는지만 확인한다.**

---

## Part A. GPIO / SIUL2

확인:

```text
S32K144
PORT + GPIO

S32K344
SIUL2 MSCR / IMCR + Dio / Port
```

실습:

```text
Button → LED Toggle
```

한 번만 구현한다.

---

## Part B. Clock

다음 경로만 확인한다.

```text
Clock Source
 ↓
PLL / Divider
 ↓
Core Clock
 ↓
Peripheral Clock
```

계산 연습을 반복하지 않는다.

---

## Part C. Timer / Interrupt

100 ms Timer 또는 RTOS Tick 중 하나를 이용하여

```text
100 ms마다 Counter 증가
```

만 확인한다.

중요한 부분:

- ISR에서는 최소 작업
- ISR → Event/Flag/Queue
- 실제 판단은 Task에서 수행

---

## 생략

이번 과정에서는 다음 실습을 별도로 하지 않는다.

- PWM 밝기 제어
- ADC → PWM
- SPI Device
- DMA Memory Copy

**1.5~2시간**

# Day 3. FreeRTOS 기반 Domain 실행 구조

## 목표

이번 스터디에서 가장 중요한 Day 중 하나이다.

도메인 컨트롤러를 다음과 같이 Task 기반으로 분리하는 방식을 이해한다.

```text
              S32K344 Domain
                    │
       ┌────────────┼────────────┐
       │            │            │
 Communication   Control       Monitor
    Task          Task          Task
       │            │            │
   상태 갱신     요청 판단     Timeout
   RX 처리       중재          Heartbeat
       │            │            │
       └────── Shared State ─────┘
```

## 학습

- Task
- Priority
- Tick
- `vTaskDelay()`
- `vTaskDelayUntil()`
- Queue
- Event
- Semaphore
- Mutex
- ISR → Task

---

## 실습

다음 Task를 만든다.

```text
Task_Input       10 ms
Task_Control     20 ms
Task_Monitor    100 ms
Task_Status    1000 ms
```

아직 실제 CAN 데이터를 사용하지 않아도 된다.

가짜 상태값을 생성하여 Task 간 데이터가 전달되도록 한다.

# Day 4. Domain SW Architecture + Request / State 모델

```text
Request = 무엇을 해달라는 요구

State = 현재 실제 상태
```

예:

```c
typedef enum
{
    REQ_NONE,
    REQ_WINDOW_OPEN,
    REQ_WINDOW_CLOSE,
    REQ_WINDOW_STOP
} WindowRequest;

typedef struct
{
    uint8_t position;
    bool moving;
    bool anti_pinch;
    bool valid;
    uint32_t last_update_ms;
} WindowState;
```

```text
        ↓
Domain Interface Layer
        ↓
Domain State
```

구조를 만든다.

---

## 역할 분리

### 통신 담당

예:

```text

ID Parsing

Driver Callback
```

### Domain 담당

예:


# Day 6. Request 검증 / 중재 / 명령 분배

## 목표

단순히

```text
HMI 요청 → ECU 전달
```

이 아니라

```text
HMI 요청
 ↓
Request Validation
 ↓
Current State 확인
 ↓
Fault 확인
 ↓
Priority / Conflict 확인
 ↓
Allow / Reject
 ↓
Target Command 생성
```

구조를 구현한다.

---

## 실습 1. Window 요청 검증

예:

```text
CLOSE Request
      ↓
COMM_FAULT ?
      ├─ YES → Reject
      ↓ NO
Anti-pinch 상태 ?
      ├─ YES → Reject
      ↓ NO
State Valid ?
      ├─ NO → Reject
      ↓ YES
CLOSE Command
```

---

## 실습 2. Door Unlock

```text
Unlock Request
      ↓
Digital Key Valid ?
      ↓
Proximity Valid ?
      ↓
Vehicle State 허용 ?
      ↓
Function ECU Command
```

# Day 7. Heartbeat / Timeout / Fault / Data Freshness

## 목표

실제 도메인 개발에서 매우 중요한 부분이다.

---

## Heartbeat

각 ECU에서 일정 주기로 상태를 전달한다고 가정한다.

예:

```text
Window ECU     100 ms
Function ECU   100 ms
Sensing ECU    100 ms
```

실제 주기는 팀 Interface Specification에서 결정한다.

---

## Timeout

예:

```text
Expected Update = 100 ms
Timeout         = 500 ms
```

이면

```c
if ((now - state.last_update_ms) > TIMEOUT_MS)
{
    state.valid = false;
    state.comm_fault = true;
}
```

형태로 관리할 수 있다.

---

## 중요한 원칙

### 잘못된 방법

```text
마지막으로 받은 값 계속 사용
```

### 권장

```text
value
+
timestamp
+
valid
+
fault
```

---

## 실습

임의로 Window ECU 상태 갱신을 중단한다.

```text
0~3초 : 정상 상태 수신
3초 이후 : 수신 중단
```

Domain에서

```text
NORMAL
 ↓
STALE
 ↓
COMM_FAULT
```

로 전환되는 것을 확인한다.

다시 상태가 들어오면 Recovery 조건에 따라 정상화한다.

---

## Fault 격리

Window ECU가 Fault라고 해서

```text
Lighting
Climate
Door Lock
```

까지 모두 정지시키지 않는다.

기능 단위 Fault 영향을 정의한다.

## 예상 시간

**2~2.5시간**

# Day 9. ESP32 / HMI Request-Result 연동

## 목표

HMI가 단순 Command Sender가 아니라

```text
Request
        ↓
Domain
        ↓
Accepted / Rejected
        ↓
실제 ECU 처리
        ↓
Completed / Failed
        ↓
HMI 상태 표시
```

구조로 동작하도록 설계한다.

---

## Request 흐름

```text
Mobile App
   ↓
ESP32
   ↓
S32K344 Domain
   ↓
Request Validation
   ↓
Target ECU
   ↓
State / Result
   ↓
S32K344 Domain
   ↓
ESP32
   ↓
Mobile App
```

---

## 구현할 데이터

### Request

```text
Request ID
Target
Command
Parameter
Timestamp
```

### Result

```text
Request ID
Result
Reject / Failure Reason
Current State
```

---

## 실습

Dummy ESP32 입력을 사용해도 된다.

```text
REQ 12 DOOR_UNLOCK
```

입력 후

```text
REQ 12 ACCEPTED
```

또는

```text
REQ 12 REJECTED AUTH_FAILED
```

가 반환되도록 한다.

이후 ECU 상태까지 반영되면

```text
REQ 12 COMPLETED
```

를 반환한다.

## 예상 시간

**2시간**

# Day 10. Domain Controller 통합 미니 프로젝트

## 목표

지금까지 만든 요소를 하나로 통합한다.

---

## 전체 구조

```text
ESP32 / Mobile
      │
      │ Request
      ▼
┌─────────────────────────────┐
│       S32K344 Domain        │
│                             │
│  HMI Interface              │
│       ↓                     │
│  Request Manager            │
│       ↓                     │
│  Domain Control             │
│       ↓                     │
│  Command Manager            │
│                             │
│  State Manager              │
│       ↑                     │
│  ECU Interface              │
│                             │
│  Fault / Timeout Manager    │
└─────────────┬───────────────┘
              │
              │ Command / State
              ▼
      S32K144 Controllers
```

---

## FreeRTOS 예시

```text
Task_CommRx       Event Driven / 5~10 ms
Task_Control      20 ms
Task_Monitor     100 ms
Task_HmiUpdate   100 ms
Task_Log        1000 ms
```

주기는 프로젝트 Interface가 확정되면 조정한다.

---

## 통합 Scenario

### Scenario 1 — 정상 Unlock

```text
Digital Key Valid
+
Near
+
No Fault
        ↓
Unlock Accepted
        ↓
Function ECU Command
        ↓
Door Unlocked
        ↓
HMI Completed
```

### Scenario 2 — ECU Timeout

```text
Function ECU Update 중단
        ↓
Timeout
        ↓
COMM_FAULT
        ↓
Door Request Reject
        ↓
HMI Fault 표시
```

### Scenario 3 — Sensor Fault

```text
Temperature Invalid
        ↓
SENSOR_FAULT
        ↓
Predictive Climate 제한
        ↓
다른 독립 기능은 정상 유지
```

### Scenario 4 — Window Safety State

```text
Anti-pinch Active
        ↓
Close Request Reject
        ↓
Window 상태 / 경고 HMI 반영
```

# 6. 통신 담당자와의 경계

현재 통신을 다른 담당자가 맡는다면 다음까지는 깊게 공부하지 않아도 된다.

## 통신 담당자 중심

- FlexCAN Instance 설정
- CAN Bit Timing
- CAN FD BRS
- Transceiver
- Termination
- Message Buffer 상세 설정
- CAN ISR / Driver 상세 구현
- Payload Byte/Bit Packing

---

## Domain 담당자가 반드시 알아야 하는 부분

- 어떤 ECU에서 어떤 State가 오는가
- 어떤 Command를 보내야 하는가
- 상태 갱신 주기는 얼마인가
- Timeout은 얼마인가
- Sequence가 필요한가
- Data Valid 조건은 무엇인가
- Fault일 때 어떤 요청을 막는가
- Request 결과를 어떻게 HMI에 반환하는가

즉,

```text
CAN을 어떻게 보내는가
```

보다

```text
무슨 정보를 언제 보내고,
도메인이 그 정보를 어떻게 판단하는가
```

가 더 중요하다.

# 10. 최종 목표

이 스터디 이후에는 다음 질문에 답할 수 있어야 한다.

- Power Window ECU에서 어떤 상태를 받아야 하는가?
- Function ECU에서 어떤 상태를 받아야 하는가?
- Sensing ECU 데이터는 언제 Invalid로 판단하는가?
- Request와 State는 왜 분리하는가?
- Command와 Request는 어떻게 다른가?
- 같은 기능에 두 요청이 동시에 들어오면 어떻게 처리하는가?
- ECU 통신이 끊기면 몇 ms 후 Fault로 판단하는가?
- Fault가 발생했을 때 어떤 기능을 제한하고 어떤 기능은 유지하는가?
- FreeRTOS Task를 어떻게 나눌 것인가?
- ISR에서 받은 데이터를 Control Task로 어떻게 전달할 것인가?
- HMI에는 요청 접수 / 거부 / 성공 / 실패를 어떻게 전달할 것인가?
- Smart Access / Climate / Ambient 판단을 어느 Module에 둘 것인가?
- 새 ECU 하나가 추가되면 Interface와 State 구조를 어떻게 확장할 것인가?

이 질문에 코드와 설계 문서로 답할 수 있으면  
**S32K344 Domain Controller 담당자로 필요한 핵심 스터디는 충분히 수행한 것**으로 본다.
